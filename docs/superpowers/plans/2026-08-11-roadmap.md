## Why this order

The five phases are sequenced by *what unblocks what*, not by visibility.

```
Phase 1  Foundation & State          ──┬──> Phase 3  Firebase Data Layer
         (test infra, context,         │
          URL state, real auth flow)   └──> Phase 2  Accessibility Conformance
                                                          │
Phase 4  Real Map Geometry  <─────────────────────────────┘
                                                          │
Phase 5  Reporting & Compliance Output  <─────────────────┘
```

- **Phase 1 first** because there is currently no test runner, no git history, and no state boundary. Every later phase edits the same seven pages; without a filter/auth context and a test harness, each phase re-touches the same files and regressions are invisible.
- **Phase 2 before Phase 3** because accessibility is contractual and cheapest to fix *before* every page grows loading/error/empty branches. Retrofitting focus management and ARIA onto async UI costs roughly double.
- **Phase 3 is the largest** and depends on Phase 1's filter context (date range must be a query parameter) and Phase 2's loading/empty state primitives.
- **Phase 4 is independent** of the data layer and can run in parallel with Phase 3 by a second engineer.
- **Phase 5 last** because report output must reflect real data and must inherit Phase 2's accessible markup.

## Phase 2 — Section 508 / WCAG 2.1 AA Conformance

**Goal:** Pass an accessibility audit. Contractual, so treated as a correctness requirement with automated gates.

### Known failures found in review

**Keyboard and focus**
- Modals (`DateRangePicker.tsx:85`, and the Settings alert form) have no `role="dialog"`, no `aria-modal`, no focus trap, no Escape handler, and do not restore focus on close.
- The user menu (`Header.tsx:126`) does not close on Escape and traps nothing; its outside-click catcher is a bare `<div>`.
- The 67-county SVG (`AlabamaHeatMap.tsx`) is entirely mouse-driven — no focusable elements, no keyboard navigation, no `<title>`/`<desc>`, no `role`. All county data is unreachable without a mouse.
- Several inputs set `focus:outline-none` with only a border-color change, which is not a sufficient focus indicator (2.4.7).

**Structure and semantics**
- No skip link, no `<main id="main">` target, no landmark on the header.
- Four hand-rolled `<table>` elements with no `<caption>` and no `scope` on `<th>`. `src/components/ui/DataTable.tsx` already exists, is accessible-ish, and is imported by nothing — rebuild it as the single accessible table and migrate all four call sites.
- Charts have no text alternative of any kind.

**Color contrast** — this is systematic, not incidental. `text-slate-500` (`#64748b`) on the card background `#1a1d2e` measures roughly **3.5:1**, below the 4.5:1 required for normal text, and it is used at 10–12px throughout every page. `text-slate-600` in the footer is worse. This needs a palette pass, not spot fixes.

**Motion** — `animate-pulse-glow`, `animate-spin`, `animate-shimmer`, and `animate-gradient` have no `prefers-reduced-motion` guard.

### Approach

Build shared primitives once rather than patching each site: `Modal`, `Menu`, and a rebuilt `DataTable`. Give every chart a `<figure>` + `<figcaption>` wrapper containing a visually-hidden data table — this is the technique auditors expect and it doubles as the screen-reader path for the map. Add a token pass raising the minimum body-text contrast, then re-verify with a contrast checker rather than by eye.

**Gates:** `vitest-axe` assertion on every page render, plus a CI job that fails the build on violations. Automated tools catch roughly 30% of issues, so the phase also includes a keyboard-only pass and a VoiceOver pass with findings logged.

**Size:** ~14 tasks. The contrast pass touches nearly every file and should land as one atomic commit.

## Phase 3 — Firebase Data Layer

**Goal:** Replace mock imports with live data, without the dashboard ever reading a raw event document.

### The core architectural decision

The consumer app writes raw events. Summing them in the browser — which is what `PantryInteractionsPage.tsx:40-43` does against mock arrays today — means one Firestore read per event. At even modest volume that is slow, expensive, and unbounded.

**Read rollups, never raw events.**

```
Written by the AccessBelt app (dashboard never reads these):
  interactions/{id}    { type, pantryId, countyFips, occurredAt, householdRef }
  visits/{id}          { householdRef, pantryId, countyFips, occurredAt,
                         itemsDistributed, familySize, ageBands, ethnicity, visitorType }
  itemRequests/{id}    { itemId, category, pantryId, countyFips, requestedAt }

Written by Cloud Functions, read by the dashboard:
  rollupsDaily/{YYYY-MM-DD}
  rollupsDailyCounty/{YYYY-MM-DD_countyFips}
  rollupsDailyPantry/{YYYY-MM-DD_pantryId}
  rollupsDailyItem/{YYYY-MM-DD_itemId}
  rollupsMonthly/{YYYY-MM_...}          # keeps YTD queries small
  counties/{fips}                        # static census/USDA metrics + current score
  pantries/{pantryId}                    # dimension doc
```

**Batch, not trigger.** A scheduled function re-aggregating the trailing 48 hours every 15 minutes beats a per-document `onCreate` trigger here: no hot-document write contention (Firestore sustains roughly one write per second per document, and a region-wide daily counter would exceed that), it tolerates late-arriving and duplicate events, and it costs less. The tradeoff is up to 15 minutes of staleness — which the UI should state honestly via a `lastRollupAt` field. That field is also what replaces the current fake "Live Sync" pill, which is a 1200 ms `setTimeout` spinner (`Header.tsx:33-38`).

**Query cost.** A 30-day, 67-county view is about 2,010 document reads. Scoping to the signed-in user's `assignedCounties` cuts that to a handful. `rollupsMonthly` keeps a YTD view from becoming 223 daily documents per county.

### Privacy and access control — must be server-side

- **Small-cell suppression belongs in the rollup function, not the UI.** Ethnicity joined to ZIP-level family counts is potentially re-identifying at small populations; the standard threshold in food-security and health reporting is n<11. Suppressing in React leaves the true counts readable by anyone who can issue the query.
- **Security rules** grant read access to `rollups*` and dimension collections only. Raw `visits` and `interactions` are unreadable by dashboard clients entirely.
- **Custom claims** carry `role` and `assignedCounties`; rules enforce county scoping. This finally makes the `permissions` and `assignedCounties` fields in `src/types/index.ts` mean something — today they are declared and enforced nowhere, so a Field Inspector scoped to one county can see and export all 67.
- **App Check** to reject non-app clients.
- **Audit log** — an `auditLog` collection, writable only by Cloud Functions, recording who exported what and when. Grant auditors ask for this.
- Note for the team: `VITE_FIREBASE_API_KEY` is **not** a secret. Firebase web API keys are public identifiers by design. `src/pages/SettingsPage.tsx:237` currently renders it masked, which implies otherwise. Real protection is security rules plus App Check.

### Client shape

A `src/data/` provider interface that both a `mock` and a `firestore` implementation satisfy, selected by env var. This is what keeps the demo working while production is built, and it lets Phase 3 land page by page instead of as one cutover. Hooks (`useRegionSummary`, `useDailyInteractions`, `useCountyMetrics`, …) all take the resolved date range from Phase 1's filter context and return `{ data, status, error }`. Every page grows loading / error / empty branches, and an error boundary wraps the shell — today a single malformed document white-screens the entire app.

**Also in scope:** swap `AuthProvider` for Firebase Auth `onAuthStateChanged` (the `status: 'loading'` field built in Phase 1 exists for exactly this, so the login page does not flash during session restore); make threshold alerts actually persist and fire via a Cloud Function; make the notification bell real.

**Size:** ~25 tasks across client and functions. Largest phase; worth splitting into 3a (rollup functions + rules) and 3b (client integration) when the detailed plan is written.

## Phase 4 — Real Map Geometry

**Goal:** Make the map either genuinely geographic or honestly labeled — and keyboard accessible either way.

`AlabamaHeatMap.tsx` renders 67 `<rect>` elements positioned by `county.grid.{x,y,w,h}`. There are zero `path` fields in the 1,249-line county dataset, and the "Alabama outline" is a hand-drawn 12-point polygon. The UI calls it an *"Interactive 67-County Alabama SVG Vector Heatmap"* (`FoodDesertsPage.tsx:93`).

A tile cartogram is a defensible choice — labels stay legible where a true choropleth would crush Alabama's small counties. The problem is the mismatch between the label and the artifact, and the loss of adjacency: "which counties border this critical zone" is unanswerable against a grid. For an audience that knows Alabama geography, presenting a grid as a vector map of the state is a credibility risk in a funding conversation.

**Recommended:** real geometry. The dataset already carries FIPS codes, which is the join key. Pull US Census TIGER/Line cartographic boundary files, simplify with mapshaper, emit a TopoJSON of the 67 counties, and project at build time so no projection library ships to the browser.

**Either way:** each county becomes a focusable element with an accessible name and value, arrow-key navigation between them, and the existing expandable county list below the map formally associated as the text alternative.

**Size:** ~8 tasks. Independent of Phase 3 — can run in parallel.

## Phase 5 — Reporting, Export & Compliance Output

**Goal:** Reports that can actually be attached to a grant submission.

- **"Print Branded PDF" is `window.print()`** (`ReportsPage.tsx:136`) and the print stylesheet only marks the footer `.no-print` — so printed output includes the sidebar and header chrome. Needs a real report renderer with a co-branded header, or at minimum a correct print layout.
- **Report history is fabricated.** Mock rows with invented file sizes, and every download hands back one of three CSVs regardless of which row was clicked (`ReportsPage.tsx:43-51`).
- **CSV hardening** (`src/utils/csvExport.ts`): no UTF-8 BOM, so Excel mangles accented community names; LF instead of CRLF; and no neutralization of leading `=`, `+`, `-`, `@` — Excel evaluates those as formulas even inside quoted fields. For a file emailed to a partner agency that is a live injection surface.
- **Scheduled email reports** via Cloud Functions, since the monthly/quarterly cadence in `mockReportTemplates` implies them.
- **Export audit logging** wired to the Phase 3 `auditLog` collection.

**Size:** ~10 tasks.

## Deferred — analytical features worth scoping after Phase 3

Not planned yet; listed so they are not lost. Each needs a product conversation before an engineering plan.

- **Per-capita normalization.** Raw "families served" always ranks large counties first. Served-per-1000-residents and *unmet need* (eligible population minus served) are the numbers that drive allocation decisions.
- **Drive-time instead of straight-line miles.** `nearestPantryMiles` is a weak access proxy in rural Black Belt counties with low vehicle ownership. Isochrones plus transit access is the defensible metric.
- **Capacity vs. demand.** The dashboard shows what was distributed, never what was requested and unmet, or whether a pantry hit its ceiling. That gap is the core funding argument.
- **Forecasting and seasonality.** Grant cycles need projected demand; food banking is intensely seasonal.
- **Cohort retention.** First-Time vs. Repeat exists as a static pie, but not the transition — do first-timers return, and does that vary by county? That is the outcomes story.
- **Supply-side data** — inventory, volunteers, referral outcomes. Everything today is demand-side.
- **Drill-down and cross-filtering.** Chart segments are not clickable; selecting a county on Food Deserts does not filter the other five pages. Phase 1's URL-synced `county` parameter lays the groundwork.
